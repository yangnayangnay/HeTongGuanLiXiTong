# 合同管理系统 - 设计报告

## 一、系统总体设计

### 1.1 设计原则

| 原则 | 说明 |
|------|------|
| **分层解耦** | Controller → Service → DAO 三层分离，降低耦合度 |
| **单一职责** | 每个类只负责一个领域的业务逻辑 |
| **开闭原则** | 通过RBAC权限配置而非硬编码来控制功能可见性 |
| **最小知识** | 层间只通过实体对象传递数据 |
| **约定优于配置** | Spring Boot自动配置，减少样板代码 |

### 4.1 Spring Boot启动流程设计

```
运行 ContractApplication.main()
    │
    ├─ 1. Spring Boot自动配置
    │      ├─ 加载 application.properties
    │      ├─ 配置数据源(Oracle JDBC)
    │      └─ 配置Thymeleaf模板引擎
    │
    ├─ 2. DataInitializer初始化(@PostConstruct)
    │      ├─ 检查数据库表是否存在
    │      ├─ 不存在 → 执行init.sql建表+插数据
    │      └─ 存在 → 跳过初始化
    │
    ├─ 3. 启动内嵌Tomcat服务器(端口8080)
    │
    └─ 4. 浏览器访问 http://localhost:8080 → 登录页面
```

### 4.2 权限控制设计（RBAC模型）

```
User ──(N:M)── Right ──(N:1)── Role ──(N:M)── Function
 (用户)          (权限表)      (角色)           (功能)

权限判断流程：
1. 用户登录 → 查询t_right获取用户的所有角色
2. 遍历每个角色 → 从t_role.functions解析功能编号列表
3. 合并为Set<String> userFunctions
4. PageController渲染页面时 → 根据userFunctions控制菜单显示
5. ApiController处理请求时 → 验证用户是否拥有对应功能的权限
6. 前端页面 → 根据权限控制按钮和内容的显示/隐藏
```

### 4.3 合同流程状态机设计

```
                    ┌─────────────┐
                    │   起草(1)    │ ← draftContract()
                    └──────┬──────┘
                           │ assignContract()
                           ▼
                    ┌─────────────┐
                    │  已分配      │ (中间态，不在state表中单独记录)
                    └──────┬──────┘
                           │ 所有countersign完成
                           ▼
                    ┌─────────────┐
                    │ 会签完成(2)  │
                    └──────┬──────┘
                           │ finalizeContract()
                           ▼
                    ┌─────────────┐
                    │ 定稿完成(3)  │ ◄──────────────────────┐
                    └──────┬──────┘                        │
                           │ 所有approve通过                │ 审批否决
                           ▼                               │ 退回定稿
                    ┌─────────────┐                        │
                    │ 审批完成(4)  │ ─── 任一人否决 ────────┘
                    └──────┬──────┘
                           │ signContract()
                           ▼
                    ┌─────────────┐
                    │ 签订完成(5)  │ ← 终态
                    └─────────────┘
```

**审批否决退回设计要点：**
- 审批否决后，合同状态退回到"定稿完成(3)"之前
- 否决意见保留在t_contract_process表中（state=2）
- 起草人可在定稿页面查看否决意见
- 修改后重新定稿，合同再次进入审批流程

### 4.4 电子签名模块设计

```
签订合同页面
    │
    ├─ 1. 加载Canvas签名画布
    │      ├─ HTML5 <canvas> 元素
    │      ├─ JavaScript监听鼠标/触摸事件
    │      └─ 实时绘制签名笔迹
    │
    ├─ 2. 签名操作
    │      ├─ 手写签名 → canvas.toDataURL() 导出PNG
    │      ├─ 清除签名 → canvas.clearRect() 清空画布
    │      └─ 确认签订 → 将签名图片数据提交到后端
    │
    └─ 3. 后端处理
           ├─ 接收签名图片(Base64)
           ├─ 保存到t_contract_file表(BLOB)
           └─ 插入合同PDF/DOCX导出文件
```

### 4.5 AI智能起草模块设计

```
起草合同页面 → 点击"AI智能起草"
    │
    ├─ 1. 前端发送请求
    │      ├─ 合同名称
    │      └─ 客户信息
    │
    ├─ 2. 后端AIAssistantService处理
    │      ├─ 读取系统设置中的AI配置(Ollama地址/模型)
    │      ├─ 构建Prompt（模板填充模式）
    │      ├─ HTTP调用Ollama API (POST http://localhost:11434/api/generate)
    │      └─ 解析AI返回的合同内容
    │
    └─ 3. 返回结果
           ├─ 成功 → 将AI生成内容填充到合同内容文本框
           └─ 失败 → 提示AI服务不可用
```

### 4.6 邮件通知模块设计

```
合同操作触发通知
    │
    ├─ 分配合同 → EmailService.sendNotification(被分配人, "新合同待处理")
    ├─ 会签完成 → EmailService.sendNotification(起草人, "合同已完成会签")
    ├─ 审批通过 → EmailService.sendNotification(签订人, "合同已通过审批")
    └─ 审批否决 → EmailService.sendNotification(起草人, "合同被否决")

EmailService.sendNotification():
    │
    ├─ 1. 读取t_settings表中的SMTP配置
    ├─ 2. 构建JavaMail MimeMessage
    ├─ 3. 通过SMTP发送邮件
    └─ 4. 发送失败 → 记录日志，不影响主流程
```

```

```

## 六、异常处理设计

| 异常场景 | 处理方式 | 用户提示 |
|----------|----------|----------|
| 数据库未启动 | Spring Boot启动失败，控制台报错 | 控制台显示连接错误信息 |
| 表不存在 | DataInitializer自动执行init.sql初始化 | 自动完成，用户无感知 |
| 登录密码错误 | 区分于其他失败场景 | "用户名或密码错误！" |
| 登录但待审核 | 特殊提示 | "您的账号正在等待管理员审核" |
| 登录但被拒绝 | 特殊提示 | "您的账号已被管理员拒绝" |
| 取消自身管理员权限 | 拦截并恢复勾选 | "不能取消自己的管理员权限！" |
| 结束时间早于开始时间 | 自动修正或提示 | "已自动调整" |
| 分配合同时无权限人员 | 列表中不显示 | 列表标签注明"(会签权限)"等 |
| 合同内容无权限查看 | 灰色占位文字 | "[您没有权限查看...]" |
| AI服务不可用 | 友好提示，不影响主流程 | "AI服务暂不可用，请检查Ollama是否运行" |
| 邮件发送失败 | 记录日志，不影响主流程 | 无用户提示（后台静默处理） |
| 重复提交 | 按钮锁定机制 | 按钮变为不可点击状态 |

## 七、设计总结

| 设计维度 | 方案选择 | 理由 |
|----------|----------|------|
| 架构模式 | B/S三层架构(Controller-Service-DAO) | 适合Web应用，部署维护成本低 |
| 权限模型 | RBAC + 后端API验证 | 灵活可扩展，前后端双重保障 |
| 模板引擎 | Thymeleaf | Spring Boot官方推荐，服务端渲染 |
| 前端框架 | Bootstrap 4.6.2 | 成熟稳定，响应式布局 |
| 数据库 | Oracle | 功能完备，序列支持编号自动生成 |
| AI集成 | Ollama本地部署 | 数据不出本地，保护隐私 |
| 邮件通知 | JavaMail + SMTP | 标准协议，配置灵活 |
| 电子签名 | HTML5 Canvas | 无需插件，浏览器原生支持 |
